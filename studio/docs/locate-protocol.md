# 图像定位协议:在图上精确找到"那个东西"

要在一张图上做圈注、箭头指向、局部高亮、Ken Burns 推向某个焦点时,**先用这套协议拿坐标,不许目测**。

契约(所有消费方共用):

```
locate(图, 目标描述) → { box: [x0,y0,x1,y1], center: [cx,cy] }   # 归一化 0..1
```

## 为什么不能目测

模型直接从一张杂乱的整图上**回归像素坐标**很不可靠(实测中心点平均误差 6.5%,圈注常落在目标外面),但**在编号网格上挑条带**很可靠。所以定位方式是:**永远不估坐标,只做离散选择。**实测同一套流程、同一个模型,只换定位方式:目测 6.5% → 本协议 2.3% 平均中心误差,且没有一例变差。(方法出处:RSVP grid-index,ACL 2025。)

## 循环(每步之间你要用 Read 看图)

```bash
node tools/locate.mjs overlay <图> --out <目录>
  → 读 <目录>/gv.png(纵向条带 1-9)和 gh.png(横向条带 1-9)
    挑出目标**压到的每一条**条带号(不是只挑中心那条,是列出全部)

node tools/locate.mjs region <图> --vids 4,5 --hids 6,7 --out <目录>
  → 读 <目录>/gc.png(该区域裁切放大 + 更细的 6×6 网格)
    再挑一次条带号。**仍然是挑号——两个阶段都不许改成估坐标,离散选择是整件事的关键。**

node tools/locate.mjs final <图> --region <上一步输出的 region> --vids 3,4 --hids 3,4
  → 最终 {box, center}

node tools/locate.mjs mark <图> --box <final 的 box> --out <目录>/check.png
  → **必做**:读 check.png。红框套在目标上 → 完成。偏了 → 带修正后的条带号重跑
    region/final(此时你已经知道偏的方向了)。永远不要跳过这步:它把"静默偏移"
    变成"一次便宜的重试"。
```

**近失是常态,不是失败。**实测中第一轮常常差一点(目标落在框角上),因为条带只挑了压得最多的那条;把straddle 的两条都填进 `--vids`/`--hids` 再跑一次就中。

## 先消歧,再定位

如果目标描述能匹配到多个实例("那个鼓",而画面里有五个),**再准的几何也救不了**。先把指代变唯一("最右边那个鼓"、"前面那条船上的鼓"),必要时问用户,然后才跑循环。

## 实现说明

- `tools/locate.mjs` 零 npm 依赖,只要 node + ffmpeg/ffprobe。ffmpeg **只用于解码/编码**(rawvideo rgb24),网格线、编号、裁切、放大、标框全在 JS 里做像素运算。
- 之所以不用 ffmpeg 的 `drawtext`/`drawbox` 滤镜:本机 homebrew ffmpeg 没编译 freetype,`drawtext` 根本不存在。上游实现依赖它,移植时直接崩了。纯 JS 版本没有这个假设,换机器也不会再踩。
- 编号用内置的 5×7 点阵数字,不依赖系统字体。
- 几何逻辑(padding、区域反推)已经冻结在脚本里,**别再临场重写一套**——上面那组精度数字只对这个实现成立。

## 降级路径(万一脚本不可用)

思路只有五行,用任何图像工具都能复现:画编号 9×9 网格 → 挑目标压到的条带 → 裁出该区域(外扩约 0.4 个条带)并放大 → 画更细的 6×6 网格 → 再挑一次 → 映射回全图(`全局 = 区域原点 + 局部 × 区域尺寸`)→ **画框出来亲眼看**。
