# Content Cover

在当前会话完成静态封面候选、实际看图与局部修订。不要嵌套运行 Codex CLI，也不要把任务转成 package、broll 或视频制作。

## 输入与准备

接受完整本地文章路径或 `SC-XXXX`。本地文章只产生本地文件，不创建飞书记录、不远端写入；SC 输入只通过 `tools/cover.py prepare` 间接复用 `tools/package_io.py fetch`，不手工拼 `lark-cli` JSON。

```bash
python3 tools/cover.py prepare --file <article.md> --slug <slug> [--groups 3] [--run-id <id>]
python3 tools/cover.py prepare --id SC-XXXX --slug <slug> [--groups 3]
```

默认 3 组，用户可指定 4 或 5 组。命令输出新的运行目录；不得覆盖既有运行目录。阅读其中的完整 `source.md`、`source.json` 和每次运行重新扫描生成的 `references.json`。详细文件合同和校验接口见 [references/manifest.md](references/manifest.md)。

不提供默认人物照片或肖像目录。只有用户授权人物封面时才通过 `--portrait-dir` 或 `.devin/cover.local.json` 指定参考库；不修改原照片。默认 `coverContract.requirePerson=false`，可以制作概念封面。用户要求本人时，在隔离派发前绑定 coverReferences 与 requirePerson=true；缺肖像只阻塞封面专项，不静默改变已确认的人物要求。

## 候选设计

先通读全文，为整批候选写一份共享 `content_brief`：内容类型、目标受众、使用情境、观众看完能做到什么、核心承诺，以及支撑主旨的原文证据；可补方法摘要和用户澄清。区分主承诺与次级论点，各组只改变视觉表达和钩子角度，不改变受众、使用情境、观看结果或主目标。当内容类型是教程时，不要把它误写成成果展示、工具观点、提示词讨论或泛行业省钱。

再从主承诺提取可被人物动作、物件或概念关系表达的看点。每组只表达一个核心意思，并记录原文摘录、hook、人物策略、文字策略和标题。创意生成前先做反向复述：只看封面会猜这是什么内容，标题与封面共同承诺什么；若答案偏离 `content_brief`，先重做概念，不用正文替错误封面兜底。

人物或概念路线按本期合同选择，有字/无字不设固定配额。人物组实际打开授权参考图，保留身份辨识度，以动作与情境表达内容，不强改五官。概念组围绕一个核心对象和一个清楚关系，不传无关肖像参考。

`subject_mode`、视觉风格与 `text_mode` 分别决定。本人方案可以无字，概念方案也可以使用摄影感、少字或强字体。先按用户指代与上下文区分封面文案和发布标题，不能看到“标题”二字就自动写入 `title`；用户明确指定的封面原句必须逐字写入 `cover_text`，并在实际图片中逐字核对，不能只改 metadata。画面文字可为空；发布标题每组必有，优先不超过 10 个可见字符，绝不超过 15 个字符，并保留正文成立的兴趣钩子。

每组必须同时设计 3:4 与 4:3 两张 PNG。两张保持同一主题、人物策略、核心对象、视觉语言和封面文案，分别重排人物、对象、文字与留白；不能拉伸、加边框或把一个比例机械裁成另一个比例。

完整视觉原则见 [docs/cover-principles.md](../../../docs/cover-principles.md)。

## 生成与检查

使用用户当前会话中已配置且授权的图像生成工具，每张图单独生成或编辑。若无生成能力，明确 blocked，不伪造图片，不擅自开通付费服务。人物组使用授权参考；双画幅保持身份、风格与内容一致，分别实际查看。概念组不传肖像参考。

把最终候选复制到运行目录的组目录，并按 schema 2 填写 `manifest.json`。每张生成后都必须实际打开查看，逐张检查主体、身份或概念、构图、手部与接触关系、文字、乱码、额外文字，以及双画幅一致性；本人组还要同时检查身份保真、自然上镜美颜和内容表演：保留骨相、五官、年龄感与自然皮肤纹理，同时优化肤色、眼下状态、小瑕疵、发型、服装、光线与镜头表现，避免塑料皮肤和过度磨皮。表情审查要如实指出笑容僵硬、嘴角被拉、视线游离或摆拍感，少用“已自然”这类缺少具体观察的强断言。再以短边约 240px 的预览检查缩略图识别。

只有实际看过且通过的组，才能把 `visual_review.passed` 写为 `true` 并记录真实观察。每组还要填写 `semantic_review`：重新写下只看封面时理解的内容，以及标题与封面共同作出的承诺；两项都与共享 `content_brief` 一致并写明判断依据后才能通过。强误读是阻断项，必须重做，不是普通审美扣分。生成成功、机器校验通过、人工看图通过、人工语义通过、用户选择与用户批准是不同状态；不得把前几项表述成用户认可。

```bash
python3 tools/cover.py validate --manifest <run>/manifest.json
```

机器校验负责组数、ID、路径、PNG 解码、实际尺寸、严格比例、短边至少 1080、标题长度、字段一致性和文件不复用。它会写同目录 `validation.json`；人工审美、肖像相似度、内容表演、语义回读与文字视觉检查仍由当前会话判断。只有机器通过，且所有组的视觉与语义人工记录都真实通过时，候选才可交付选择；这些 attestation 都不是机器对质量的证明。

向用户展示各组两张可点击图片、对应发布标题和一句差异说明，称为“候选”或“待选择”。不要自动替用户排名或选定。

## 修订与回写边界

用户选组后，只按明确意见局部修改，并同步复查两个比例；没有被要求改变的概念、人物、文字和标题保持锁定。修订产物仍先标为待检查，不继承旧的目检通过状态。

只有用户明确选定标题或授权写回最终封面方案时，才可通过既有确定性 helper 写入 SC 文档的 `封面方案` 区段；不得手工改飞书、自动发布或改外部标题。本地文章运行始终不做远端写入。

最终交付选定组的两种比例 PNG 与一个标题，并保留候选、提示词、来源、实际参考路径、manifest 和验证报告。不要写全局记忆，也不要覆盖原文、人物原图或旧封面。

## 统一产物位置

执行前读取 `docs/artifact-layout.md`。统一入口 `../output/<SC-XXXX>/` 只放可直接使用的资源，分类目录内平铺中文内容名文件；无内容不建目录。合同、报告、日志、工程与旧版本留在仓库 workspace 或隐藏 `.制作资料`。内部验收后同步可用资源到用户目录，不再放 README 和制作流程目录。
